# Dashboard

Owner-only web dashboard for operational visibility and controlled bot actions. Exposes an aiohttp web server with live message archive, historical backfill, audit logging, and send-as-bot capabilities.

## Overview

The dashboard provides:

- **Bot health and metrics** — uptime, guild count, latency, audit event count, cog list, feature flags
- **Guild inventory** — connected servers with member counts, channel counts, permission summaries, and categorized channel listings
- **Unified message archive** — real-time live ingest of all bot-visible messages (guild + DM) into a single MessageStore, plus a separate legacy DMStore
- **Historical backfill** — on-demand or automatic backfill of channel, guild, and DM message history, respecting Discord permissions
- **Audit log** — append-only, filterable, paginated event log for all dashboard actions and bot events
- **DM archive** — bot-visible DM conversations (users who DMed the bot or received DMs from the bot)
- **Message search** — full-text LIKE search across archived messages with guild/channel/author filters
- **Send as bot** — owner-only DM and guild message sending with rate limiting, permission checks, and audit logging
- **Reply to messages** — reply to individual guild messages with Discord MessageReference support

### What the dashboard CAN see

- All guilds the bot is a member of (name, ID, member count, channels, permissions)
- All channels within those guilds (names, types, positions, categories, bot permissions)
- All messages the bot can see — ones it receives (on_message) and ones it sends
- DM conversations where the bot is a participant
- Audit events generated by dashboard operations and bot lifecycle

### What the dashboard CANNOT see

- Human-to-human DMs where the bot is not a participant
- Messages in channels the bot lacks `read_messages` or `read_message_history` permission
- Private threads the bot is not a member of
- Message content in channels where the bot cannot see history
- Discord Moderation/Admin actions beyond what the bot's audit log events expose

## Configuration

All settings are controlled via environment variables in `.env`:

### Required

| Variable | Description |
|---|---|
| `DASHBOARD_ENABLED` | Master toggle (`true`/`false`) for the dashboard server |
| `DASHBOARD_AUTH_TOKEN` | **Required** when enabled. Strong random token for authentication |

### Optional — defaults shown

| Variable | Default | Description |
|---|---|---|
| `DASHBOARD_HOST` | `127.0.0.1` | Bind address |
| `DASHBOARD_PORT` | `8011` | Bind port |
| `DASHBOARD_PUBLIC_BIND` | `false` | When `true`, binds to `DASHBOARD_HOST` instead of forcing `127.0.0.1` |
| `DASHBOARD_SESSION_SECRET` | _(auto-generated)_ | Session signing key. Auto-generated if unset (printed once to console) |
| `DASHBOARD_OWNER_IDS` | _(falls back to `OWNER_IDS`)_ | Comma-separated Discord user IDs allowed to access the dashboard |
| `DASHBOARD_MESSAGE_DB_PATH` | `./data/dashboard_messages.db` | SQLite path for unified MessageStore (guild + DM messages) |
| `DASHBOARD_AUDIT_DB_PATH` | `./data/dashboard_audit.db` | SQLite path for audit log |
| `DASHBOARD_GUILD_ARCHIVE_ENABLED` | `true` | Enable live message archiving for guild channels |
| `DASHBOARD_DM_ARCHIVE_ENABLED` | `true` | Enable DM archiving for bot-visible conversations |

## Access

### Default (localhost only)

```
http://127.0.0.1:8011/
```

### SSH tunnel

```bash
ssh -L 8011:127.0.0.1:8011 user@server
# Then open http://127.0.0.1:8011/ locally
```

### Tailscale

```bash
DASHBOARD_ENABLED=true DASHBOARD_HOST=100.x.y.z DASHBOARD_PORT=8011
```

### Reverse proxy (recommended for external access)

```
DASHBOARD_ENABLED=true
DASHBOARD_PUBLIC_BIND=true
DASHBOARD_HOST=127.0.0.1  # Still bind to localhost; let proxy handle TLS
```

Then configure nginx/Caddy with HTTPS + basic auth/OIDC in front of `http://127.0.0.1:8011`.

## Chat Flow

1. **Overview page** shows bot health, guild list in sidebar, and DM thread list in the home view
2. **Select a guild** from the left rail to see its channels (grouped by category)
3. **Click a channel** to load messages — the unified MessageStore is queried first, then falls back to live Discord fetch (auto-backfill) if empty
4. **Composer** appears at the bottom of the message view — type a message and press send (or Ctrl+Enter)
5. **Reply to a message** by clicking the "↩ Reply" button on any message — sets up a reply context with MessageReference support
6. **DMs** are listed on the home sidebar — clicking opens the DM thread with the same composer/reply UX

### DM Limitations

- Only bot-visible DMs are archived (bot is a participant in the conversation)
- No human-to-human DMs are accessible
- DM channels are identified by their Discord channel ID or the other user's ID
- If the bot has no shared guild with a user, DM delivery may fail silently

### Backfill Limitations

- Backfill is capped at `DASHBOARD_BACKFILL_MAX_MESSAGES_PER_CHANNEL` (default 500) per channel
- Guild backfill processes up to `DASHBOARD_BACKFILL_MAX_CHANNELS_PER_RUN` (default 50) channels
- Backfill respects Discord permissions — skips channels where bot lacks `read_message_history`
- Only text-based channels are backfilled (no voice, stage, forum)
- Jobs are tracked in SQLite with status transitions: queued → running → completed/failed/cancelled
- DM backfill requires the DM channel to exist in the bot's private channels
- Rate-limited to `DASHBOARD_RATE_LIMIT_BACKFILLS_PER_HOUR` (default 5)

### Send-as-Bot Behavior

- All sends are rate-limited by actor+target pair (5/min default, configurable)
- Content length is validated against `DASHBOARD_MAX_MESSAGE_CHARS` (default 1800)
- Permission-checked: bot must have `send_messages` and `read_message_history` in the target channel
- DM sends require the target user to share a guild with the bot or have open DMs
- Every send attempt is audited (requested → success/failure with reason)
- Sent messages are archived in both the MessageStore and DMStore (for DM sends)
- Mentions can be suppressed via `DASHBOARD_SUPPRESS_MENTIONS`
- @everyone mentions are blocked unless `DASHBOARD_ALLOW_EVERYONE_MENTIONS` is true

### Reply Behavior

- Uses Discord `MessageReference` when the original message can be fetched
- If the original message cannot be fetched, sends a plain message (no reference)
- Validates the target message exists in the specified channel
- Falls back to legacy send if MessageReference construction fails
- Reply attempts are audited separately from plain sends (requested → success/failure)
- The reply endpoint resolves `channel_id` from the MessageStore if not provided in the request body

## Security

- **Owner-only**: All API endpoints (except `/healthz`, `/api/session`, `/api/static-config`) require authentication
- **Auth methods**: Bearer token via `Authorization` header, or session cookie after login
- **Session cookies**: HTTP-only, SameSite=Lax, configurable TTL (default 8 hours)
- **CSRF protection**: All POST endpoints require a CSRF token (from session or `X-CSRF-Token` header)
- **Rate limiting**: Token-bucket rate limiter on DM/guild message sends (per actor+target pair)
- **IP hashing**: Source IPs are SHA-256 hashed (12-char prefix) in audit logs
- **Content redaction**: Discord tokens, OpenAI keys, API keys, bearer tokens, passwords, and private keys are regex-redacted in audit log previews and stored content
- **No secrets in UI**: Auth tokens, API keys, session secrets, and full exception traces are never exposed to the frontend. The `/api/static-config` endpoint deliberately omits all secrets.
- **Permission checks**: Guild/channel sends verify bot has `send_messages` and `read_message_history` permission
- **DM scope**: Only bot-participant DMs are archived; no scraping of private user data
- **Security headers**: All responses include `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and a restrictive `Content-Security-Policy`
- **Directory traversal protection**: Static file serving validates resolved path is under the static directory
- **CSRF toggle**: `DASHBOARD_REQUIRE_CSRF` can disable CSRF (not recommended for production)
- **Auth failure audit**: Failed auth attempts are logged with hashed IP and user agent

## Frontend

The dashboard uses **vanilla JavaScript** (no frameworks) with a single-page application pattern:

### URL Hash Routing

| Hash | View |
|---|---|
| `#/overview` | Home / overview page with guild rail and DM list |
| `#/guild/{guild_id}` | Guild detail with channel sidebar |
| `#/guild/{guild_id}/channel/{channel_id}` | Channel messages view |
| `#/dm/{channel_id}` | DM thread messages |
| `#/audit` | Audit log browser |
| `#/backfill` | Backfill job manager |

### UI Features

- **Sidebar rail** — guild list with icons, plus audit/backfill nav items
- **Channel sidebar** — guild channels grouped by category, with permission indicators
- **Message list** — Discord-style chat bubbles with author, avatar, timestamp, attachments, embeds
- **Composer** — text input with character count (`{len}/{max}`), warning at >90%, error at over limit
- **Reply UI** — "↩ Reply" button on each message sets reply context; cancel button clears it
- **Composer labels** — labels change based on channel type ("Send to #channel", "Send DM to @user", "Reply in #channel")
- **Send indicator** — spinner during send, toast notifications for success/error/rate-limit
- **Load older** — paginated "Load older messages" button
- **Backfill prompt** — appears when store is empty, triggers on-demand backfill
- **Refresh** — manual refresh of current view
- **Auto-backfill** — when a channel is first viewed, if the store is empty, live-fetches recent messages from Discord

## Architecture

```
bot/dashboard/
├── __init__.py          # Package exports (stores, services, config, permissions, redaction)
├── config.py            # Environment variable loading → DashboardConfig dataclass
├── server.py            # aiohttp AppRunner lifecycle + hourly cleanup loop
├── routes.py            # HTTP route handlers + route registration
├── auth.py              # Auth middleware (bearer + session), SessionStore, CSRF, login/logout handlers
├── audit_store.py       # SQLite audit log (WAL, retention, pagination, event type constants)
├── dm_store.py          # Legacy SQLite DM archive (WAL, retention, per-user + per-message tables)
├── message_store.py     # Unified SQLite store for guild + DM messages (single messages table + dm_threads)
├── backfill.py          # BackfillJobStore (SQLite job tracking) + BackfillService (async Discord history fetcher)
├── services.py          # Business logic (summary/cache, rate limiter, send/reply operations, live message fetch)
├── permissions.py       # Reusable permission check utilities (can_view_channel, can_send_messages, etc.)
├── redaction.py         # Content safety: secret redaction, preview truncation, HTML sanitization, CSP builder
└── static/
    ├── index.html       # Dashboard HTML shell with sidebar, composer, messages container
    ├── dashboard.css    # Styling (Discord-like theme, responsive, dark mode)
    └── dashboard.js     # Client-side JS (vanilla SPA, hash routing, state management, API calls)
```

### Key Data Stores

- **MessageStore** (`message_store.py`): Unified SQLite store for all bot-visible messages. Schema includes `messages` table (guild + DM messages with attachments, embeds, metadata) and `dm_threads` table. Backed by WAL mode, thread-safe with `threading.RLock`. All I/O dispatched via `asyncio.to_thread`. Schema version 1.

- **DMStore** (`dm_store.py`): Legacy SQLite store for bot-visible DM conversations. Separates user metadata (`dm_users`) from messages (`dm_messages`). WAL mode, thread-safe. Used as fallback when MessageStore is unavailable.

- **BackfillJobStore** (`backfill.py`): SQLite-backed job tracking with status machine: `queued` → `running` → `completed`/`failed`/`cancelled`. Prevents duplicate active jobs per target. Stale `running` jobs are reset to `queued` on dashboard restart.

- **AuditStore** (`audit_store.py`): Append-only SQLite audit log. All event types defined as module constants. Supports paginated queries with filters. IPs are SHA-256 hashed (12-char prefix). Content previews are truncated and redacted.

### Startup Flow

1. `LLMBot.setup_hook()` → `setup_background_tasks()`
2. `_start_dashboard()` background task loads config via `load_dashboard_config()`
3. If `DASHBOARD_ENABLED=true`: creates AuditStore, DMStore, MessageStore, BackfillJobStore, BackfillService, DashboardServices, DashboardServer
4. aiohttp AppRunner starts on configured host:port with all routes registered
5. Hourly cleanup loop: expired sessions, audit retention, DM retention, message store retention
6. Shutdown: `LLMBot.close()` calls `dashboard.stop()` which cancels cleanup task, resets stale backfill jobs, and stops the aiohttp runner

### Integration Points

- Dashboard observes bot state through `DashboardServices` (narrow interface)
- Live message archiving hooks into `on_message` for DMChannel and guild text channel messages
- Audit store is separate from other SQLite databases
- BackfillService uses Discord `channel.history()` for message fetching
- MessageStore and DMStore are dual-fed: both capture new messages in `on_message`, and sent messages archive to both
- No circular imports: dashboard imports from bot core, not vice versa
